#003 — Standardise authentication retry policy across all services — fixed intervals ≤ 3 s for user-facing flows; exponential backoff reserved for background/batch jobs only ActiveORG

Date: 2026-08-02
Governs files: src/auth/client.py, src/auth/retry.py, services/*/auth/client.py
Decision: Standardise authentication retry policy across all services — fixed intervals ≤ 3 s for user-facing flows; exponential backoff reserved for background/batch jobs only
Rejected: Per-service ad-hoc retry configuration
Reason: Inconsistent retry strategies across services caused cascading delays during the July auth outage; a shared policy enforced via the org-memory ensures all teams stay aligned
Future implication: All new services must import the shared retry configuration from the platform team's auth library rather than implementing their own

#002 — Use fixed 2-second retry intervals for authentication API — exponential backoff causes unacceptable UX latency under normal load patterns Active
Source MR: !17 — Fix login latency regression — switch auth retry to fixed intervals
Date: 2026-07-28
Governs files: src/auth/client.py, src/auth/retry.py
Decision: Use fixed 2-second retry intervals for authentication API — exponential backoff causes unacceptable UX latency under normal load patterns
Rejected: Exponential backoff (Memory #001)
Reason: Load testing showed p95 login time jumped to 14 s under exponential backoff during burst traffic; fixed 2 s intervals kept p95 under 6 s with no increase in error rate
Future implication: Revisit if the authentication service introduces adaptive rate-limit headers; exponential backoff may then be appropriate for background jobs only
Decided by: @arjun, @sanya

#004 — Refresh authentication tokens proactively 5 minutes before expiry rather than reacting to 401 responses Active
Source MR: !21 — Proactive token refresh before expiry
Date: 2026-08-05
Governs files: src/auth/tokens.py, src/auth/client.py
Decision: Refresh authentication tokens proactively 5 minutes before expiry rather than reacting to 401 responses
Rejected: Reactive refresh on 401 error
Reason: Reactive refresh adds a full round-trip latency on every token expiry; proactive refresh keeps sessions seamless and eliminates a class of transient auth failures that previously triggered unnecessary retries
Future implication: The retry module (Memory #002) and the token refresh module must coordinate — a 401 received during the 5-minute proactive window should short-circuit retries and trigger immediate refresh
